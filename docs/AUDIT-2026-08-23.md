## 1. What the audit found healthy

Recorded because an audit that only lists problems misrepresents the system.

**Admin authorisation is centrally enforced and has already survived its worst
bug.** `middleware.ts` classifies private paths from `context.url` — the
pathname Astro actually routed on — after an incident where `//api/admin/settings`
and `/%61pi/admin/settings` classified as public while Astro served them as
admin. Unsafe methods on `/api/admin/*` additionally require a same-origin
`Origin` and reject `sec-fetch-site: cross-site`. No admin route re-implements
this, which is why grepping the route files for an auth call finds nothing —
the check is one layer up, where it cannot be forgotten.

**The headless surface is not an unguarded copy of the admin surface.**
`/api/v1/*` routes go through `validateHeadlessRequest()`: a developer API key,
an origin allowlist resolved per store, and an audit row. The OpenAPI document
is the only public member.

**The retired payment webhook is a tombstone, not a deletion.**
`/api/webhooks/autolaris` answers `410` with an explicit code. A deleted route
would 404 and invite a retry to be re-pointed at something new; this one cannot
mutate payment state and says why.

**Discipline markers are real.** One `TODO`-class comment in 59k lines of
source, and it is a `// lazy:` naming its own ceiling
(`notifications.ts`: no retention job, one row per order forever). 504 tests
pass, `astro check && tsc --noEmit` reports 0 errors across 375 files, and the
dependency list carries nothing that a platform feature already does.

**Five installs run the current product.** `zanobyshop.shop`, `carukesi.com`,
`skincarebpom.shop`, `taniniaga.shop` and `zvara.shop` all serve Astro 7.2 and
all answer `401` on `/api/admin/health` — the admin boundary holds on every one.

## 2. Findings

### 2.1 `STATUS.md` names one install, and it does not resolve

`STATUS.md` § "Known installs" lists `permatamall.shop` as the only install.
That hostname has no DNS record at all:

```
$ dig +short permatamall.shop
(empty)
$ curl https://permatamall.shop/
curl: (6) Could not resolve host
```

Meanwhile the five installs in §1 are unlisted. The document that tells a
future reader where this product actually runs is pointing at the one place it
does not.

This matters beyond tidiness: `STATUS.md` is what decides where a fix has to be
adopted. **Owner: `STATUS.md`.** Fixed in this branch.

### 2.2 The CAPI outbox has no clock of its own

`drainCapiOutbox()` is called from exactly two places, both request handlers:
`/api/meta-event` and `/api/v1/tracking/events`. The hourly cron in
`worker.ts` runs `ensureSchemaUpgraded`, `purgeExpiredAbandonedOrders`,
`collectOperationalHealth` and `evaluateOperationalAlerts` — and does not drain
the outbox.

So a delivery failure is retried only when the next visitor arrives. Backoff
caps at `CAPI_MAX_BACKOFF_MS` (60 minutes), which assumes something will be
along within the hour to act on it. On a store between campaigns that is not
true, and a Purchase that failed at 23:50 waits for traffic rather than for
time.

The system already *detects* this — `collectOperationalHealth` counts pending
rows whose `next_retry_at` has passed — so the cron computes the number and
then does not act on it. The binding, the schedule and the query all exist;
what is missing is three lines wiring them together. The store's pixel ID and
CAPI token are a D1 read the cron is already positioned to make.

Not observed failing: `zanobyshop.shop` shows 3115 of 3115 events `sent`.
This is a liveness gap, not an outage.

**Owner: a product change.** Not fixed here — it needs a decision about how
the scheduled path resolves store ad config, which is the same question a
multi-store cron would ask.

### 2.3 An auto-rotating hero is structurally incompatible with Speed Index

Reported in #53 and partly addressed in #54: `startHero()` used to run at parse
time, so the first advance landed 4 s in and painted a fresh LCP candidate.
Moving the start to `load` helped LCP but did not fix the page, and the
follow-up measurement says so plainly. Home page, three runs after the fix
shipped:

| | LCP | Speed Index |
| --- | --- | --- |
| median of 3 | 3.2 s | 6.0 s |

The LCP element is still a slide at `left: -409px` — the track has advanced
before the trace ends — and Speed Index is unchanged, because it integrates
visual completeness over the whole trace and a page that keeps changing never
reaches it. Deferring the start moves the cost; it does not remove it.

The honest options are a product decision, not an implementation one:

1. **Drop the timer.** Keep the dots, keep swipe, remove auto-advance. Fixes
   LCP and Speed Index outright.
2. **Keep the timer and accept ~6 s Speed Index on the home page.** Defensible
   if the rotation earns its keep — but nothing currently measures whether it
   does.

Recommend (1) unless someone has data for the carousel. A 480px single-column
storefront home exists to route people into products, and the products list is
directly below the fold.

### 2.4 Third-party tags dominate blocking time, and deferral cannot fix that

Product page, median of four runs after #54 deferred `gtag.js`:

```
Facebook            530 ms blocking   226 KB
Google Tag Manager  218 ms blocking   153 KB
everything else       0 ms
```

Total Blocking Time moved 740 ms → 778 ms median, i.e. not at all. This was
predictable in hindsight and is worth writing down so it is not re-attempted:
deferring a script by 2500 ms moves *when* it parses, and Lighthouse's trace
runs long enough to include it either way. Deferral is still right — it takes
the download off the critical path, and FCP and LCP both improved — but it buys
nothing on TBT.

TBT on these pages is therefore a floor set by Meta and Google, not a defect.
The only lever that would move it is sending fewer tags, which is the opposite
of what the storefront is for. **No action. Recorded so the next audit does not
open the same ticket.**

### 2.5 `label-content-name-mismatch` needed two attempts

Worth recording because the first fix was wrong in an instructive way. The
brand link failed WCAG 2.5.3 because its visible text was not contained in its
accessible name. The first attempt (#54) added the missing space between
`{leadWord}` and `{trailingWords}` — a real defect, but not this one. The audit
kept failing.

The actual cause was the monogram: a decorative `Z` rendered as a text node
beside a wordmark that already spells the name. `aria-hidden` keeps it out of
the accessible name but not out of what the audit reads as visible text.
Drawing it from `data-monogram` via CSS `content` removes the text node
entirely (#55). Fixed.

### 2.6 Test coverage has a shape worth knowing

84 test files against 154 non-test modules in `src/lib`. Eighteen modules have
no direct test; ranked by size:

```
province.ts 191   tenant-content.ts 111   catalog.ts 97   autolaris-balance.ts 95
ui-variants.ts 91  store-ads.ts 81        geo.ts 77       env.ts 75
rts-scoring.ts 65  gtm.ts 54              (8 more under 31 lines)
```

Most are thin or exercised through their callers. Two are worth a direct test
on their own merits rather than for the count:

- **`store-ads.ts`** resolves the pixel ID, CAPI token and Google Ads
  identifiers every tracking path depends on. A silent misresolution here
  disables tracking store-wide and nothing fails loudly.
- **`rts-scoring.ts`** scores return-to-sender risk, which is money.

`province.ts` at 191 lines is almost certainly a data table and does not need
one. **Owner: `TASKS.md`** if adopted.

### 2.7 `/landing-page` — #45 item 1 is stale, item 2 is not

The index route now exists and serves:

```
zanobyshop.shop/landing-page    200
carukesi.com/landing-page       404
skincarebpom.shop/landing-page  404
```

The two 404s are stores with no landing pages, so the honest question is
whether a store with an empty list should 404 or serve an empty state. The
home page links to it unconditionally, so today a fresh install ships a link to
a 404. **Owner: #45**, which should be re-scoped to that rather than closed.

Item 2 of #45 — `brand-contamination` failing in any install whose catalogue
images live in `public/` — is unchanged and still fails on `zanobyshop.shop`
(503/504 pass there against 504/504 here). The test scans source for
references; the references are in D1. Until it can read the database, or is
scoped to the product's own assets, every install runs with one permanently
red test, which is worse than no test: a real contamination would not be
noticed.
